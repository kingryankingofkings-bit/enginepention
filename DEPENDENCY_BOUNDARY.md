# Dependency Boundary

Per Master Execution Prompt §3.2, every non-engine artefact used during build or
testing is listed here with its purpose, license, version, whether it ships, and
why it is boundary infrastructure rather than an engine subsystem.

The governing distinction: **"custom-built" applies to the product's
implementation, not to rebuilding the operating system, compiler, GPU driver, or
hardware.** A permitted interface is not permission to import its sample
implementation (§3.2, final paragraph).

### Third-party engine subsystems

**None, and none permitted.** §3.1 prohibits source or binary middleware for
rendering, scene graphs, entity systems, physics, collision, destruction, cloth,
fluids, animation, IK, motion matching, audio, spatial audio, networking,
navigation, AI, scripting, UI, editor widgets, terrain, vegetation, procedural
generation, particles, video, asset importing, serialization, reflection,
profiling, crash reporting, telemetry, and platform abstraction.

Concretely, the following are **prohibited** and absent, per §16:

> PhysX, Bullet, Jolt, Havok, FMOD, Wwise, Recast/Detour, Dear ImGui, Qt, SDL,
> GLFW, Boost, Mono, the .NET runtime, Lua, Python-as-engine-scripting,
> Chromium, and analogous third-party subsystems.

§3.1 and §16 both state the rule that most often gets rationalised away, so it is
restated here: **a permissive license does not satisfy the custom-build
requirement.** MIT, BSD, Apache, zlib, and public-domain implementation code are
prohibited on the same terms as proprietary code. The constraint is on
authorship, not on licensing.

### Content and assets

All test and demonstration assets are original to this project or procedurally
generated by project code. No engine sample content, commercial asset, or
scraped asset enters the tree. Per §10 the demonstration project contains no
borrowed commercial or engine sample assets.

## Audit procedure

Before every release candidate (§3.3.9):

1. **License audit** — every artefact above re-verified for version and terms.
2. **Binary dependency audit** — linker map inspected; every external symbol
   traced to a permitted OS or driver boundary.
3. **Symbol and string audit** — the tree scanned for identifiers and string
   literals characteristic of prohibited libraries.
4. **Code-similarity audit** — results recorded in
   [PROVENANCE_LEDGER.md](PROVENANCE_LEDGER.md).

Results, including failures, are recorded. A clean audit that was not actually
run is a §4 violation.

## Change control

Adding anything to this file requires an ADR that establishes it is boundary
infrastructure under §3.2 and not an engine subsystem under §3.1. There is no
"small utility library" exemption, because that is the exact shape of the
rationalisation the rule exists to prevent.
