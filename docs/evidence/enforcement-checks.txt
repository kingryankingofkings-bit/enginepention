enforced and the Rust half ran on convention - which is the situation ADR-0004
rule 2 exists to prevent. Edges are read from each manifest's path dependencies,

is the complete edge list rather than a sample of it.

Robin Hood invariant, verified to be load-bearing, 2026-08-21
================================================================================

Backward-shift deletion under Robin Hood ordering may stop at the first entry
sitting on its ideal slot. Under plain linear probing that rule is wrong. The
insert-side displacement is therefore load-bearing for the erase-side rule, and
the two must be checked together rather than separately.

Displacement disabled, simple erase kept - the exact combination that was the
bug one commit earlier:

  FAILED: 22 tests, 108994 checks, 6 failures

With displacement restored:

  PASSED: 22 tests, 704719 checks, 0 failures

Measured probe lengths before and after the change, from a standalone program
over freshly inserted keys:

  HashMap    1,000 entries    15 -> 5
  HashMap   10,000 entries    30 -> 8
  HashMap  100,000 entries   146 -> 25
  NameTable  1,000 names      11 -> 5
  NameTable 10,000 names      47 -> 10
  NameTable 100,000 names    133 -> 18

The 100,000-entry cases are the reason this was found at all. The probe test in
the previous commit stopped at 500 entries, where the difference is invisible.

Query acceleration, verified against its defects, 2026-08-21
================================================================================

PN-OBJ-002's criterion is a cost statement - query cost independent of total
entity count for a fixed match set - so it is checked as the number of entities
the query examines, not as a duration. A duration would be a property of this
machine and could not be reported as a result under the project's performance
rules; an operation count is a property of the algorithm.

Five defects, each introduced alone.

=== The driver is the first named storage, not the smallest ===
The behaviour the increment replaces. Note that the criterion test alone catches
it only because it now runs both naming orders; with the large storage named
first, the query walks every entity in the world to find fifty.
  FAILED: 24 tests, 283402 checks, 5 failures

=== The driver is the largest named storage ===
The comparison inverted, which is what a copy-paste of the selection loop most
easily produces.
  FAILED: 24 tests, 283402 checks, 7 failures

=== Statistics not reset at the start of a query ===
A query that returns early - a named component nobody has - would otherwise
leave the previous query's numbers standing, and every assertion about a cost
would be reading a stale one.
  FAILED: 24 tests, 283427 checks, 5 failures

=== matched incremented before the completeness test ===
Makes matched equal examined, so the two numbers stop distinguishing "looked at"
from "visited" and the acceleration claim becomes unfalsifiable.
  FAILED: 24 tests, 283518 checks, 4 failures

=== examined reported as the total entity count ===
The instrument lying in the direction that would make a genuine regression
invisible.
  FAILED: 24 tests, 283402 checks, 7 failures

=== With all five restored ===
  PASSED: 24 tests, 1971837 checks, 0 failures

The check counts are again lower on every failing run than on the passing one,
because the brute-force comparison aborts on its first disagreement. The count
alone is not a result.

One property is not on this list: that the visitor receives components in the
order they are named rather than the order they are stored. It has no defect to
introduce, because the argument order is fixed by the parameter pack at compile
time while the driver is chosen at run time - a build that got it wrong would
not compile against a visitor taking two distinct component types. Structural,
not tested, and said here rather than left to look like an oversight.

Scene identity and reference repair, verified against its defects, 2026-08-21
================================================================================

Six defects, each introduced alone. Five were caught. The sixth was not, and
that is the useful result on this list.

=== A saved reference not checked for aliveness ===
The failure the whole mechanism exists to prevent. A component still holding a
handle to a destroyed entity, whose slot has since been reused, maps through the
slot index to the *replacement* entity's ordinal. The file then contains exactly
the aliasing the generational handle prevents, laundered through a save, and
nothing about the file or the load reports it.
  FAILED: 17 tests, 7885 checks, 2 failures

=== Component types written in registration order rather than sorted ===
Which module registers a component type first changes with build configuration.
The console's config file had this same hole one increment earlier.
  FAILED: 17 tests, 9151 checks, 1 failure

=== Identities not erased from the lookup index on destroy ===
A destroyed object's id would still resolve, to a slot now holding a different
object.
  FAILED: 17 tests, 9225 checks, 1 failure

=== The id counter not advanced past a restored identity ===
A loader creates entities with the ids the file names. Left alone, the next
entity created after a load is handed an id the file already used.
  FAILED: 17 tests, 9225 checks, 1 failure

=== An unknown component type refused rather than skipped ===
Each type's block carries its length so a reader can step over a type it does
not know. Removing that turns a scene saved by a build with one more component
type from "loads without it" into "does not load".
  FAILED: 17 tests, 9222 checks, 1 failure

=== Component records written in storage order rather than sorted by ordinal ===
  PASSED: 17 tests, 9225 checks, 0 failures

That last one is a failure of the test, not of the code, and it is the second
time this project has found one this way. The byte-for-byte round-trip test
compared a world against its own reload - and the reload inserts components in
the order the file lists them, so it inherits the same storage order the save
was written from. Both sides moved together and the comparison held.

The property that actually needs holding is that the file is a function of the
world's *content*, not of the edit history that produced it. Two worlds are now
built with the same entities, the same identities and the same components, one
of them having had a component removed and re-added - which moves that entity to
the end of the dense array and changes nothing else - and their files are
compared. Re-checked with the record sort removed:

  FAIL two_worlds_with_the_same_content_write_the_same_file (1 of 84 checks failed, aborted)
  FAILED: 18 tests, 9309 checks, 1 failure

And restored:

  PASSED: 18 tests, 9412 checks, 0 failures

Separately, every single-byte corruption of a saved scene - each offset in turn,
one byte flipped - is asserted to be rejected rather than loaded. That is a
property of the framing from PN-PLT-020 rather than of this increment, but it is
worth asserting at the level a caller actually uses.
